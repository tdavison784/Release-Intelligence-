# Render evaluation — pipeline-level R17 metrics, 2026-10-02

Run on `p3ll/render` after merging `p3-learning-loop` @ 2937ce7, so the applicability, groundtruth
and knowledge lanes are all in. Every one of the 28 eval entries ran twice, once without
`--render` (before) and once with it (after). helm v3.16.1, kubectl/kustomize v5.7.1, network on.

    GITHUB_TOKEN=$(gh auth token) bin/ri -state <warm state> eval -o json > before.json
    GITHUB_TOKEN=$(gh auth token) bin/ri -state <warm state> eval -render -render-json stats.json -o json > after.json
    eval/render/tools/r17_join.py after.json stats.json

With `-render`, each environment case is first rendered with its own configuration (its values
files; for cases that have none, nothing customer-specific can be rendered), and
`impact.Input.Render` is wired to those renders.

## The potential, and why it needs facts (R11)

From `r17_join.py` (expected impact links of the env cases):

| | count |
|---|---|
| expected affected links (action / review / informational) | 73 |
| … missed by the pipeline today | 55 |
| … missed, but their change is restated by a complete customer render | **8** (6 action-required, 2 review) |
| expected **not-affected** links whose change a customer render also restates | **4** of 32 |

The 8 links are where render-backed knowledge can move applicability:
istio E1, E2; karpenter E2, E7; kyverno E1, E3, E5, E8. For example, kyverno E1 ("the background
controller loses its Secret read/write") is `rbac-permission-removed secrets/list` in the customer's
render. But the 4 not-affected links show that a rendered restatement is *not* exposure by itself:
the chart changes, and this environment still does not care. Turning the 8 into hits without the 4
becoming false positives takes exactly what the loop is built for. That is a fact whose exposure
names the deciding object/field (`rendered-change`), plus a verified consequence. A render delta
alone stays at most REVIEW (`TestRenderDeltaAloneNeverYieldsAction`).
