# Milestone 1 implementation: consumer-aware investigation (lane consumer)

`PLAN-M1.md` §3 changes 1–8 with the §4 tests, on branch `p6di/consumer`. Everything is additive. The
pipeline's graph, traversal, validators, classification and approval are unchanged; v1–v8 prompts are
byte-frozen (digest-tested) and replay unchanged.

### Why a separate consumer graph

Consumer mode is opt-in (`relations.WithConsumers`, `relations.BuildConsumerGraph`). Only a v9 agent session
builds it, over the same bundle, with the pipeline's relationship rules (`agent.WithRelations(relations.WithCatalog(…))`,
wired in `cmd/ri`). It is stored as a run artifact (`derived/agent/consumers/<side>/<graph-id>.json`, producer
`investigate.agent.consumers@v1`). This has two effects:

- The stored graph and its traversal stay exactly what they were. New unresolved edges there would add impact
  paths, and so change classification; M1 changes no policy input.
- `expand_graph` results and v6–v8 dossiers do not change, so v1–v8 transcripts still replay.

The mount detail is a structured field, not text in `Detail`, because `Detail` is part of the edge id; this keeps
the traversal's edge ids valid in the consumer graph. `reads-file` points provider → consumer, like every edge.

## Fix: generated ConfigMap data (lane consumer2, ledger D-0005)

**Cause, verified.** A workload mounted a ConfigMap generated by kustomize `configMapGenerator` from an
application config file. The consumer graph had the `references` edge and no `reads-file` or unresolved edge for
the file's paths. Three facts combine:

1. The snapshot collects YAML files only (`internal/env/repo.go` `classifyRepoFile`), and only those with Kubernetes
   documents. A generator's non-YAML source file, or a YAML one without `apiVersion`/`kind`, is not in it.
2. `generatorData` skipped the missing `files:` source (`continue`) but still stored the generator's entries. So
   the data was "known and empty", not "unknown". `configData` returned ok, `readsFile` iterated zero entries, and no
   edge and no gap followed. (The `continue // its data is not in the snapshot` in `readsFile` fires only for an
   undefined ConfigMap; there, too, nothing was recorded.) `keysOf` likewise took the empty set for the full key set.
3. The overlay that builds the generator is version-independent (a `not-applicable` render pair with one render). The
   graph loads only complete pairs, so the generated object, with its data and hash-suffixed name, is in a render
   artifact but not among the graph's objects. The workload in the graph is the environment file, which names the
   unhashed generator.

The smoke below confirms (1) and (3) on a non-development bundle.

**Fix: consumer rules v2** (`relations.WithConsumerRules`; default v2; producer `relations.builder@v1+consumers@v2`).
Only the session-built consumer graph changes. The environment snapshot, the stored relationship graph and every
policy input stay as they were.

- **Render fallback.** When a generator source is missing, the generated object is taken from a render of the
  same side: the side's render of a complete pair, or the one render of a version-independent overlay.
  - The overlay must build the generator: its target is `kustomize:<dir>`, or an Application whose source path is
    a kustomization, and its `resources`/`bases`/`components` tree must include the generator's directory.
  - The object must be named as kustomize names it: the tree's `namePrefix`/`nameSuffix`, then `-<hash>` (ten
    characters of kustomize's hash alphabet) unless `disableNameSuffixHash`. It must be in the generator's namespace.
  - The snapshot's own entries (files present, literals) are kept; the rest come from the render.
  - Each `reads-file` edge cites the render artifact, line and text. `file.dataFrom` names the rendered object, the
    render target and why the snapshot lacked the data; the rule is `graph.reads-file@v2:rendered-data:<via>`. The
    generated node also cites the render.
  - Several matching objects with different data are not decided (fail closed).
- **No silent drops.**
  - Data no source holds becomes an unresolved `reads-file` edge (`missing`, rule `…@v2:unknown-data:<via>`,
    `file.path` empty, `file.configKey` the key or empty for all). Two cases: a generator source absent with no
    usable render, or a ConfigMap the snapshot does not define. The reason says which source is absent and why no
    render helped; the line cites the generator's `files:` entry.
  - `trace_consumers` reports such an edge in `gaps`, both for the configuration and, when the reading container
    also mounts a traced Secret, as "whether it names a path under <mount> is not established". The dossier's
    consumer gaps carry the same lines.
- **Secrets.**
  - `secretGenerator` keys come from the generator (`files`, `literals`, `envs`, or the render), so a path's key is
    checked against them.
  - A key of a generated Secret whose keys are not known (an env source absent) is `inferred` with the reason.
  - A runtime-created placeholder (e.g. a controller's Secret) is unchanged: its absence is already the trace's
    "created at runtime" gap.
- **Other `continue`s checked** in the consumer builder:
  - a nameless generator (kustomize rejects it);
  - an object that states its own data;
  - a key the container does not see (items, `subPath`, `configMapKeyRef`);
  - `resolve` never returns nil;
  - line lookups (an unlocated line is a trace gap already).
  None hides a reachable relationship.
- **Replay.**
  - Rules v1 reproduce the D-0001 graph byte for byte. Checked by building six fixture graphs with the pre-fix
    code and with v1.
  - A v9 session writes `consumerRules` into its transcript header (from v2 on).
  - A replay uses the rules its transcript names; a header without the field means v1, which covers every
    transcript recorded before D-0005.
  - Checked on the recorded shop-de smoke (`M1s-v9-shop-de-20261020-f6c23796`), replayed with this code: 65 of 65
    calls are identical (arguments, outcome, result digest), status `submitted`, and the replayed header names no
    rules. The M1 attempt-1 transcripts should replay the same way. They were not replayed here, because they are
    development cases.
  - Environments without generated data give the same graph under both rules, apart from the builder name.
  - `agent.WithConsumerRules` pins the rules explicitly.

Tests: `relations/consumers_generated_test.go` and `agent/consumers_generated_test.go`. They cover the render
fallback with prefix and hash, both sides, the cited line, the negative controls (another container's mount, a
look-alike name, another namespace), the no-render gap, an undefined ConfigMap, generated Secret keys, disagreeing
renders, the hash suffix disabled, v1 stability, trace and dossier gaps, and replay pinning. `TestV9Replay` is

## How to run v9

v8 stays the default prompt until the M1 gate is met (mission §13); select v9 explicitly:

```sh
go build -o bin/ri ./cmd/ri
scripts/phase5/snapshot.sh 03b6ff43 "$SCRATCH/K0"          # K0 knowledge snapshot
cp -Rc .ri "$SCRATCH/state"                                  # never write the shared cache
DO_NOT_TRACK=1 bin/ri -state "$SCRATCH/state" -offline eval -investigations \
  -case <case> -knowledge "$SCRATCH/K0" -work "$SCRATCH/work" -run-id <run-id> -arm <arm> \
  -agent -agent-model claude-sonnet-5-5 -agent-prompt investigate-agent/v9 -save
# replay a stored v9 run deterministically:
bin/ri -state "$SCRATCH/state" -offline eval -investigations -case <case> -knowledge "$SCRATCH/K0" \
  -agent -agent-driver replay -agent-replay-dir eval/investigations/results/<run-id> -run-id <new-id>
```

`ri investigate --agent … --agent-prompt investigate-agent/v9` runs one investigation. `ri investigate dossier
<inv-id> <item>` rebuilds a v9 dossier with the run's stored consumer graph.

## Known limits

- Paths are matched only in ConfigMap data. The following are not matched: container `args`/`command`, literal
  `env` values, Secret data (redacted), relative paths, and one-segment paths not under a mount (taken for
  routes).
- A projected volume whose sources carry no items and might each hold the key gives `inferred` edges to each
  source, unless the snapshot's data decides.
- Objects created at runtime have unknown keys, so a key's existence is not checked for them (the trace reports
  the object as created at runtime). Generated Secrets: keys from the generator or the render (rules v2); with an
  env source absent and no render, a key is `inferred`.
- Kustomize generator `behavior: merge` / patches to generated ConfigMaps are not applied to snapshot data. The render
  fallback (rules v2) applies only when a generator source is missing, and then reads the rendered object, which
  has them applied. Disagreeing renders of the same generator leave its data unknown.
- The render fallback reads data only. The workload in the graph is still the environment file of a
  version-independent overlay, not its rendered (patched) object, so an overlay patch to volumes or mounts is not
  seen. Generator matching ignores `components` name transformers and `nameSuffix`/`namePrefix` set by
  transformer configs other than the kustomization fields.
- Rules are fixed per session: a replay uses its transcript's rules. An `-llm-exchange` session started before
  D-0005 and resumed after it builds a v2 graph, so its dossiers differ from the recorded rounds.
- The completion check uses the TO side and the item's exposure roots. With no roots there is no check, and
  `trace_consumers` reports that as a gap. Retrieval means the object came back from `trace_consumers` or
  `get_rendered_object`, or its environment file from `read_artifact`, in the item's own session. A dossier
  listing does not count.
- `ri investigate mcp --run` (read-only) serves no consumer graph: `trace_consumers` is refused there.
- Assessments are AI prose except the verified entries' citations; nothing checks that a verified statement
  says what its quote says (the same limit as every agent record).
- v9 is not the default: `DefaultPromptVersion` stays `investigate-agent/v8` until the M1 gate is met (commander
  review of D-0001); `TestDefaultPromptIsTheNewest` allows that pinned default.
