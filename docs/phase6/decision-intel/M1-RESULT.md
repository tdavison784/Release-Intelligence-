**(a) fails in 6 of 6, so the gate is not met.**

Every ROT assessment traces Certificate → Secret → Deployment (`checkout` and `ledger`/nginx, mounted at `/tls`).
Every run then stops there and lists it as unknown: "What the containers read under /tls is not established. No
configuration in the snapshot names a path there" (US r1, `ci-f86a125e0d17`).

**Cause: a code defect, not the model.** The consumer graph has `references` Deployment `ledger` → ConfigMap
`ledger-nginx` (volume `conf`, `/etc/nginx/conf.d`). It has no `reads-file` edge and no unresolved edge.
- `ledger-nginx` is generated by kustomize `configMapGenerator` from `ledger.conf`.
- That file is not in the environment snapshot. It appears only as an excerpt of `kustomization.yaml`.
- Its full data is in the rendered manifest.
- `relations/consumers.go` `readsFile` looks up generated data in `g.gen`, finds none, and skips with
  `continue // its data is not in the snapshot` — the silent drop the plan prohibited.
- The smoke case could not show this: `shop-de` mounts no Secret or ConfigMap.

**What did improve over B0 (v8):**
- **Consumers traced.** `trace_consumers` was used 9–10 times per case. Every ROT assessment names both consuming
  Deployments, their mount path, and the nginx container. B0 never opened a consumer.
- **(c) is right everywhere.** In US, every run states that `mesh-root-ca` is explicit `Never` in the
  `platform/pki` prod overlay, and that the leaf Certificates inherit `Always`. In EU, every run states that all
  three inherit `Always`.
- **The CA consequence is reached without the config:**
  - US: "The CA key is unaffected because mesh-root-ca is pinned to Never" (r2); "mesh-root-ca is protected by its
    explicit Never setting" (r3).
  - EU: "A rotated mesh-root-ca key changes the CA that signs checkout-tls and ledger-tls" (r1); "previously issued
    leaf certificates stop chaining to the CA bundle consumers may hold" (r3).

  This is why (b) and (d) are partial: the difference is explained, but the consumer that holds `ca.crt` stays
  unknown, so neither case reaches a supported conclusion.
- **The completion check worked.** In EU r3 (`ci-f86a125e0d17`) it recorded two untraced Deployments as
  investigation gaps.

**Verdicts (agent; not authoritative):**
- ROT: `potentially-affected` in all 12 item-runs.
  - US: same as B0's H.
  - EU: B0 had `affected` on `ci-86548e9a2300` (CU), so it is now H.
- This is v9's provisional-unless-supported rule working as designed while the trust consumer is unknown.
- **False-safe: none.** The RHL items are `not-affected` or `potentially-affected`; their expected class is not
  affected.

**Policy safety holds.** The authoritative classification (`impact-report.json` findings and summary) is identical to
B0's in all 6 case-runs.

### Decision

The fix stays inside M1 (mission §13: no M2 work before the gate). Lane `consumer2` (D-0005):
- **Generated ConfigMap data:** when the generator's source files are not in the snapshot, read the generated
  object's data from the rendered manifest. This is generic, and matches the generator to the rendered object
  through its hash suffix.
- **No silent drops:** when the data is unavailable anywhere, emit an unresolved edge, which surfaces as a
  `trace_consumers` gap.
- **Tests:** a `configMapGenerator` fixture whose source file is absent from the snapshot.

Then repeat the gate (attempt 2) with new run ids.

**(a)** Every ROT assessment now carries the full hop: "Certificate payments/ledger-tls → Secret ledger-tls →
Deployment ledger and ConfigMap ledger-nginx, which names /tls/tls.crt, /tls/tls.key and /tls/ca.crt" (EU r1).

**(d)** The two cases differ in substance in every run:
- US: "The root CA is unaffected because it is pinned to Never" (r3); "mesh-root-ca pins Never, so the CA key is
  stable" (r2).
- EU: "Rotation of the mesh-root-ca key at renewal would invalidate leaf certificates issued by the old CA key, and
  clients that trust the old root would be affected" (r1).

**(b) is partial.** `ca.crt` is reached, but its role as the trust anchor is spelled out only once: EU r3, "mesh-root-ca
rotation would change CA key and require re-issuance of leaf certs and trust redistribution (ledger ca.crt)". Two
causes:
1. **The checkout half of the mTLS is never read.** `checkout`'s container command holds
   `curl … --cacert /tls/ca.crt --cert /tls/tls.crt --key /tls/tls.key` (`env/apps/payments/base/checkout-deployment.yaml`
   L28). Paths in container command, args and env values are not matched: this is a documented M1 limit. Every run
   says, correctly: "checkout mounts /tls but nothing in the snapshot names which files it reads".
2. **The model rarely interprets the directive.** It names the file but seldom says that nginx verifies clients
   against it.

So the "nothing pins a leaf key" conclusion (Phase 0's E) is never drawn. US stays H, because "whether any peer pins
the key" stays unknown.

**Verdicts (agent; not authoritative):**
- ROT: `potentially-affected` in all 12 item-runs.
- RHL: `not-affected` 8, `potentially-affected` 4.
- False-safe: none.

**Policy:** authoritative classification identical to B0 (checked for attempt 1; attempt 2 changes only the consumer
graph, which the classifier never reads; rechecked below).

**Cost:** $0.79–1.21 per case, 52–59 calls, 215–254 s.

**Decision:** fix the documented limit inside M1, since it is exactly criterion (b) and mission B3 ("ConfigMap →
environment variable or volume → application"). Lane `consumer3` (D-0006) matches absolute paths in container
`command`, `args` and literal `env` values against the same container's mounts. Then comes attempt 3. The product owner
decides the gate on the best attempt (D-0003).

### What the gate does not show (for the audit)

1. **The verdicts do not separate the environments.** All 12 ROT item-runs are `potentially-affected`, in US and EU

   rule: every run keeps "whether the workloads reload certificates" and "whether any peer pins the key" as
   unknowns, and static config cannot settle either.
   - Phase 0's natural Claude Code drew "nothing in the repo pins leaf keys" as a repository-scoped conclusion and
     scored E on both cases.
   - This is calibration, not safety. Agent verdicts never reach the classifier, and clearance belongs to M4

2. **Development cases only.** cert-manager was used to find and fix the three defects in attempts 1–3 (generated
