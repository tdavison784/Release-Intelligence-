## 0. Executive summary (what a declarative definition MUST know)

1. **Plain unprefixed semver, dual live majors.** Tags are bare `X.Y.Z` (78 tags: 71 stable, 7 prereleases `1.0.0-alpha1/-alpha2/-beta1/-rc1`, `2.0.0-rc1`, `3.0.0-alpha1/-beta1`; 0 junk); latest stable **3.9.0** (2026-09-22). A line is X.Y. **2.19 is maintained alongside the 3.x lines**: 2.19.6 shipped 2026-06-30 on the `2.19` branch, three months after 3.8.0. Policy evidence: the org-wide `.github/RELEASING.md` states the distribution "track[s] 2 releases in parallel" (e.g. 3.x + 2.19 branches active after 3.0). 1.x is dead: last release **1.3.20 (2024-12-10)**; majors are rare by design ("common for a distribution to go multiple years without a major release"). 1.x forked from Elasticsearch OSS 7.10.2 (1.0.0 April 2021); 2.0.0 (2022-05); 3.0.0 (2025-04-29, JDK 21 minimum, Lucene 10).
2. **Per-release notes are per-version markdown files, read at `main`.** `release-notes/opensearch.release-notes-X.Y.Z.md` (73 files at main). **A release's own file exists at its own tag for only 38/71 releases** (2.19.0's own file is absent at the 2.19.0 tag); files land on main around release time, so the source is read at `main` (the traefik/elasticsearch fixed-ref precedent). 69/71 releases have their file at main. The two exceptions: **2.19.2 has no notes file anywhere** (not at its tag, not at main — its notes exist only as the GitHub release body, verified [200 API]) and **2.19.6's file exists only at the 2.19.6 tag** (the tag commit IS "Add release notes for 2.19.6"; it never merged to main). GitHub release bodies carry the same `## Version X.Y.Z Release Notes` document for every release (verified for 2.19.2) → declared as the fallback member of a fallbackGroup (the api.github.com anonymous quota is the standing tax).
3. **Notes section vocabularies differ by era** (all in the same per-version file):
   - **3.6+ (generated)**: `### Features` / `### Enhancements` / `### Bug Fixes` / `### Maintenance` — generated from PR labels since 3.6 (`CHANGELOG.md` is a tombstone pointing at the PR search).
   - **2.0–3.5 (Keep a Changelog)**: `### Added` / `### Dependencies` / `### Changed` / `### Deprecated` / `### Removed` / `### Fixed`; **3.0.0 additionally has `### Breaking Changes`** (23 bullets: Lucene 10, JDK 21, removals).
   - **2.0.0 (custom rich)**: `### Breaking Changes in 2.0` (with `####` topic subsections), `### Security Fixes`, `### Features/Enhancements`, `### Bug Fixes`, `### Build & Infrastructure`, `### Documentation`, `### Maintenance`, `### Refactoring`, `### Tests`.
   - **1.x (gitlog dumps)**: `* __PR title__` + author + commit bullets, no `###` sections at all — readable as whole-doc items but classification is heuristic-only (recorded as a gap).
   - `CHANGELOG.md` itself is a Keep-a-Changelog "Unreleased" working file (released content is moved out into the release-notes file); rejected as a source (redundant, tombstoned ≥ 3.6).
4. **The AsciiDoc reuse claim is FALSE — the fork does NOT keep the migrate_N_0.asciidoc conventions.** The elasticsearch record justified `format:adoc` partly by "opensearch (the fork … keeps the same migrate_N_0.asciidoc conventions)". Verified: the OpenSearch repository has **no AsciiDoc anywhere** — `docs/` at main contains only a leftover `build.gradle`; no `MIGRATION.md`, no `breaking-changes/` directory, no migration docs at any tag (the fork moved its documentation to the separate **Jekyll/markdown** `documentation-website` repository early in 1.x). The per-version breaking-changes channel is `documentation-website@main` `_about/breaking-changes.md` [200]: a cumulative **plain markdown** page with `## X.Y.Z` sections (`1.x`, `2.0.0`, `2.5.0`, `2.18.0`, `2.19.0`, `3.0.0`) and proper `### topic` headings (e.g. "JDK requirement", "Index version", "Transport NIO plugin") — the direct twin of Elasticsearch's `docs/release-notes/breaking-changes.md`, except that ES's file embeds AsciiDoc definition lists (needing `format:adoc` + labelParagraphs) while this one is native markdown needing neither. The page states the policy: "breaking changes are only introduced between major version releases" → attached with `releaseKinds: [major]`. The 2.5.0/2.18.0/2.19.0 sections are minor-introduced exceptions to that policy and carry plugin-side changes (k-NN default engine, neural-search text_embedding) — recorded as a gap, not three windowed sources.
5. **Artifacts** (all hosts REACHABLE): Docker image `docker.io/opensearchproject/opensearch:X.Y.Z` (bare tags; anonymous token flow worked during research — 200 tags/list — but Docker Hub anonymous is the known rate-limit/401 risk; `mirror.gcr.io/opensearchproject/opensearch` [200] mirrors it and `public.ecr.aws/opensearchproject/opensearch` [200, anonymous ECR token] carries **all 72 stable tags from 1.0.0 to 3.9.0** — the docs-site install page recommends the ECR path); tarballs on **`artifacts.opensearch.org`** [200, S3-backed] — the all-plugins bundle `releases/bundle/opensearch/X/opensearch-X-linux-x64.tar.gz` (200 at 1.0.0, 1.3.0, 2.0.0, 2.19.6, 3.9.0) and the bare core `releases/core/opensearch/X/opensearch-min-X-linux-x64.tar.gz` (200 at 1.0.0, 2.0.0, 2.19.2, 3.9.0); source = GitHub tag archive [200]; community **Helm chart** `opensearch` in `opensearch-project/helm-charts` (gh-pages index [200], 169 entries): recent chart version == appVersion == server version, but 35 appVersions have >1 chart version (chart-only fixes) and **2 server releases never ship a chart (1.2.0, 1.2.2)** → `lookup` by appVersion + `optional` (the argo-cd shape), not `template`.
6. **Compatibility pins are machine-readable, in two eras.** The bundled Lucene pin: `buildSrc/version.properties` (`lucene = 8.8.2` at 1.0.0 → `8.10.1` at 1.3.0 → `9.1.0` at 2.0.0 → last at 2.18.0) then **`gradle/libs.versions.toml` from 2.19.0** (`lucene = "9.12.1"` → `10.1.0` at 3.0.0 → `10.5.1` at 3.9.0; a Gradle version catalog, TOML not YAML → `version:pattern` for both eras). Unlike feared, **3.x does NOT use a Lucene fork**: the catalog pins plain `org.apache.lucene:lucene-core` (verified on `repo1.maven.org` [200]: 8.10.1, 9.12.1, 10.5.1 jars). Bundled JDK (`bundled_jdk = "25.0.4.1+1"`, vendor `adoptium`, toml era only) has no stable anonymous URL for the exact vendor build (same gap as elasticsearch).

## 2. Release notes [200]

- Per-version file presence (git cat-file at tag and at main, all 71 stable tags): **38 at-tag, 32 main-only, 1 nowhere** (2.19.2). 2.19.6's file exists at its own tag only (never merged to main — 2.x maintenance commits stay on the `2.19` branch). → source reads at `main`; fallback = GitHub release body; exceptions recorded for 2.19.2/2.19.6 on the repo-file member are unnecessary because the fallback answers.
- GitHub release bodies [200 API, tags/2.19.2]: body IS the release-notes document (`## Version 2.19.2 Release Notes` + `### Added/Dependencies/Changed/Deprecated/Fixed`), 0 release assets (releases are tag markers; artifacts live on artifacts.opensearch.org/registries). Assets empty on sampled releases → no release-asset artifacts.
- Section eras: see summary §0.3. Classification covers both vocabularies by section regex (`(?i)^(Bug Fixes|Fixed)$` etc.); the 2.0.0 `####` subsections under `### Breaking Changes in 2.0` inherit the parent's breaking classification.
- The notes files' header line "Compatible with OpenSearch and OpenSearch Dashboards version X.Y.Z" is the only machine-readable Dashboards-compatibility statement (Dashboards versions in lockstep with the server; separate product, noted as related).

## 3. Breaking changes / migration guidance (the adoc-reuse test) [200]

Conclusion: `format:adoc` is **not** reused by this product — a full-fidelity measurement point for the fork-reuse claim (see the record): the fork's docs are Jekyll markdown, so the construct elasticsearch credited to "opensearch keeps the same conventions" was never exercised here. Everything this product needs is markdown + properties/TOML pattern reads.

## 6. Compatibility and lifecycle

- Lifecycle evidence is the org policy, not a product page: `https://raw.githubusercontent.com/opensearch-project/.github/main/RELEASING.md` [200] — "track 2 releases in parallel" (active branches after 3.0: 3.x + 2.19); majors only when "significant breaking changes" accumulate; OpenSSF best-practice vulnerability fixing in "actively maintained versions". `opensearch.org/support` and `/releases/maintenance-policy` are **404** [verified] — no Elastic-style dated EOL table exists; statements in the definition quote the track-2 policy plus the observable last-release dates (1.3.20, 2024-12-10 = 1.x finale; 2.19.6, 2026-06-30 = 2.x still patched).
